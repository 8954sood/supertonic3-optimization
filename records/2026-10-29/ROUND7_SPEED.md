# 7차: 배속 기능과 원본 2배속 누락 원인 조사

## 현재 상태

F1200 구조·가중치, 엔진v2, CPU1·실제 denoising8회를 유지한다. 새 학습이나 모델 축소는 하지 않았다. 사용자가 main에서 직접 커밋·푸시하도록 지정해 검증된 엔진v2 `35d7ffc`까지 main에 반영했다. 이후도 같은 정책이다. 모델·데이터의 Hugging Face 고정 리비전은 바뀌지 않았다. [6차 성능](ROUND6_ENGINE.md), [F1200 공개·재현 검증](PUBLICATION_F1200.md)을 함께 본다.

최신 집계는 `results/round7_speed_summary.json`이며 `python experiments/summarize_round7.py`로 원시 JSON에서 다시 만든다. 이번 ASR은 이미 사용한 개발 문장 KO/EN 각1개를 M1/F1로 반복한 검사다. 독립 시험이나 MOS가 아니다.

## 배속 옵션과 기능 검사: 통과

`Engine.synthesize(speed=...)`는 이미0.7~2.0을 지원했으나 합성 CLI에 인자가 없었다. `synthesize.py`와 benchmark에 `--speed`를 추가하고 측정값에 설정 속도를 남겼다. 기본1.05를 유지한다. 모델 duration을 speed로 나누는 기존 경로이며 출력 파형의 tempo나 샘플레이트를 바꾸지 않는다.

- CLI가 범위 밖0.69·2.01과 NaN·무한대를 모델 로드 전에 거부했다. API도 모두 거부했다.
- 실제 1코어/1GB 서버에서 standard F / 엔진v2 × M1/F1 × KO/EN ×0.7·1·1.05·1.5·2.0 = **40회** 생성했다. 순차 실행한 각 프로세스가 guard480MB/reserve80MB를 통과했다.
- 속도1.0 대비 발화 길이1/speed 관계를3samples 이내에서 모두 확인했다. KO M1은0.7에서7.980초,1.0에서5.586초,1.05에서5.320초,1.5에서3.724초,2.0에서2.793초다.
- **20개 파형 모두 기존 F와 엔진v2의 float32 샘플이 bit-identical**했다. RMSE/max difference는0이다. 새 정수 커널의 수치 오차가 이번 배속 오류의 원인은 아니다.

근거: `experiments/speed_sweep.py`, `results/round7_speed_{base,v2}_{M1,F1}.json` 및 각 guard, `round7_speed_identity_{M1,F1}.json`, `round7_speed_cli_validation.json`. Sweep은 shape당1회 생성이며 warm-up이 없으므로 이 시간으로 엔진 속도 향상을 주장하지 않는다.

메모리 감시기는 자식 프로세스 트리의 합산RSS도 감시하도록 보완했다. 기존 단일 자식 RSS 필드는 유지한다. 직접 자식은60MB 미만인 상태에서 그 하위 프로세스의64MiB 할당으로 합산 예산을 넘기도록 검사했고, 감시기가 해당 프로세스 그룹을 종료했다(`round7_guard_process_tree.json`). 공유 페이지 중복 계산 가능성이 있으며 50ms 표본 감시이지 OS의 강제 상한은 아니다. benchmark CPU 시간에는 기다려 회수한 자식 프로세스 시간도 포함하며 범위를 기록한다.

## 원본과 F1200의 발음: 2배속 실패

고정 원본 FP32·CFG4·최대50스텝을 같은 문장·음색·seed42로 로컬에서 생성했다. 원본 참조만 CPU4이며 서버CPU1 추론 시간과 비교하지 않는다. 4개 ONNX의 SHA-256을 검사한다. 원본8/16스텝도 원인 분리용으로만 추가했다. 학생은 계속8회다.

Whisper base INT8·CPU1, M1/F1 합산 결과:

| 속도 | 원본50 KO CER | F1200 KO CER | 원본50 EN WER | F1200 EN WER |
| --- | ---: | ---: | ---: | ---: |
| 0.7 | 3/50 (6%) | 8/50 (16%) | 0/22 | 0/22 |
| 1.0 | 0/50 | 0/50 | 0/22 | 0/22 |
| 1.05 | 미측정 | 0/50 | 미측정 | 0/22 |
| 1.5 | 8/50 (16%) | 2/50 (4%) | 1/22 (4.55%) | 4/22 (18.18%) |
| 2.0 | 22/50 (44%) | 23/50 (46%) | 9/22 (40.91%) | 10/22 (45.45%) |

표본이 작고 같은 문장이 반복되므로 전반적인 모델 우열을 의미하지 않는다. 1.5도 음색에 따라 오류가 났고0.7에서는 반복이 생겼다. 2.0에서 원본8은 KO25/50·EN9/22, 원본16은 KO23/50·EN9/22로 단순 스텝 변경도 해결하지 못했다.

사용자는 F1200의1→1.5→2배속 청취 후2배속 누락·뭉개짐을 확인했다. 같은2배속 원본50→F1200 비교의 구체적인 피드백:

> 원본은 안녕하세요 오래된 컴퓨터에서도 빠르게 에서 끊기고 우리가 만든건 안녕하생 컴퓨터 에서 빠르게 음성을 이라고 말해

원본도 문장 뒤가 빠지고 학생에는 앞부분 발음 변형도 있다. **원본2배속을 깨끗한 교사 정답으로 간주하지 않는다.** 품질 기준은 정상 속도 원본 FP32 최대 품질이다. 원본에도 문제가 있다는 이유로 학생의 추가 오류를 허용하지 않는다.

근거: `round7_original50_speed{,_asr}.json`, `round7_original50_slow{,_asr}.json`, `round7_original{8,16}_fast{,_asr}.json`, `round7_speed_asr_{M1,F1}.json`, `round7_original50_feedback.json`. 청취 WAV는 Git에서 제외하며 경로와 SHA-256은 기록한다.

## 파일 끝 자르기와 텍스트 분할 대조군: 해결 안 됨

`experiments/diagnose_native_speed.py`로 로컬 원본50/F1200의 KO M1/F1을 다시 생성했다. 보코더의 잘라내기 전 파형을 직접 보관해 같은 출력과 비교했다.

- 잘라낸 부분은 M1 **0.063061초**, F1 **0.064762초**다. 보존 구간은 bit-identical했다.
- 잘라내기 전 원본 M1도 ASR상 `안녕하세요 오래된 컴퓨터에서도 빠르게`에서 끝난다. 원본 M1 CER는 전/후 모두8/25다. 파일 끝 자르기만 고쳐서 빠진 문장을 복구할 수 없다.
- 문장을2개 또는 절을3개로 나눠 각각 native2배속 생성 후 무음 없이 연결해도 복구되지 않았다. 두 모델 모두 ASR 오류가 늘었다. 짧은 출력에서는 인식기 반복 환각도 발생했으므로 CER를 청취 점수로 해석하지 않는다.
- 분할은 진단용이며 기본 경로에 넣지 않았다. 분할별 duration 예측이 달라 총길이도 달라진다. 파형 tempo 변경이나 추가 denoising은 없다.

`results/round7_native_diagnostic_{original50,F1200}{,_asr}.json`에 조각·길이·파형 해시가 있다. F1200의 이 대조군은 로컬 CPU1이며 서버 파형과의 동일성을 주장하지 않는다. 상류 Hub main과 SDK 고정 참조의4개 ONNX도 모두 현재 원본과 같은 해시였다(`round7_upstream_model_audit.json`).

## 후처리 배속 실험: 보류

정상 속도 생성 후 별도 tempo 필터를 적용하는 경로도 잠시 실험했다. 사용자가 원본 비교와 모델 내부 해결을 선호해 기본 경로에 넣지 않았다. 코드는 로컬 `.private/deferred-tempo-round7/`에 보관했다. 서버 프로젝트 전용 가상환경에만 선택 의존성 imageio-ffmpeg0.6.0이 설치돼 있다. 시스템 패키지는 변경하지 않았다. M1 실험은 완료했으나 F1은 자체 실험 프로세스를 중단해 최종 guard 기록이 없다. 로컬 기존 FFmpeg도 공유 라이브러리 문제로 실행되지 않아 채택하지 않았다. 기본 requirements에는 추가하지 않았다.

## 엔진v3 부분합 후보: 채택하지 않음

v2의 안전한 int16 부분합 결합 범위를 K8→K16으로 늘리고, 최악 경계를 증명할 수 없는 블록은 기존 정수 경로로 되돌렸다. 가중치·양자화·스텝은 그대로다. unsafe16 블록 비율은 평균22.87%, 최대48.65%로 v2의 약0.61%보다 높다.

8개 실제 가중치/shape microprobe의 S32 결과는 같았고 속도는 약0~12.6% 개선됐다. 실제 서버 전체 TTS의2쌍 교대 fresh-process 측정:

| 문장 | v2 시간 중앙값 | v3 시간 중앙값 | 각 쌍 가속비 |
| --- | ---: | ---: | --- |
| KO short | 5.581초 | 5.401초 | 1.030 / 1.037 |
| EN short | 5.180초 | 5.193초 | 1.000 / 0.995 |

영어에 일관된 이득이 없고 v3의 전체 파형·장문 검증도 수행하지 않아 **v2를 유지**했다. 드라이버는 종료시 원래 v2 라이브러리를 복구했으며 해시로 확인했다. 정수 연산 동일성 검사를 전체 음성 품질 검증으로 확대 해석하지 않는다.

후보 소스는 `experiments/exact_int8_v3.c`이며 기본 커널은 `native/exact_int8.c`다. 빌드 예:

```bash
python -m ziglang cc -target x86_64-linux-gnu.2.28 -mcpu=znver1 -O3 \
  -Wall -Wextra -Werror -fPIC -shared experiments/exact_int8_v3.c \
  -I native/include -o native/libexact_v3.so
```

`experiments/paired_native_kernels.py`는 입력 라이브러리를 자식 프로세스 사이에서만 교체한다. 전용 실험 디렉터리에서 쓰며 동시에 다른 추론을 실행하지 않는다. `round7_v3_actual_probe.json`의 과거 label `row8`은 v2, `safe_accum`은 v3다. 전체 측정은 `round7_paired_v2_v3.json`이다. 후속 드라이버는 샘플 이름 충돌 방지를 위해 출력 stem을 포함한다.

**공유 서버의 이번 v2 측정 RTF는 약1.05였다.** 6차의0.943~0.971은 당시 세션 결과이며 지속적인 실시간 보장이 아니다. 세션 간 성능 변동을 숨기지 않으며 ARM으로 환산하지 않는다.

## 이어서 할 일

2배속 native 품질은 아직 미해결이다. 모델을 더 줄이거나 불완전한 원본2배속 정답으로 재증류하지 않는다. 모델 내부 개선을 학습으로 시도한다면 먼저 **정상 속도 원본50의 내용과 음색을 보존하는 빠른 정답** 생성 방법을 검증해야 한다. 학습 자료에만 속도 변환을 적용하는 안도 원본 그대로의 출력과 구분해 표시하고 내용·피치·자음 검사 후 고려한다. 단순 latent 시간 보간은 위상·음높이 보존이 확인되지 않아 정답으로 채택하지 않는다.

그 뒤 실제8회 추론에서 속도별 발음·정상속도 회귀와 사용자 청취를 검사한다. 현재 새 학습·모델 업로드는 시작하지 않았다. 정상1.0~1.05의 F1200과 엔진v2를 기준으로 유지한다.
