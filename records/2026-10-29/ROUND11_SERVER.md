# 11차: 서버 API와 문장 단위 스트리밍

## 범위와 출발점

사용자가10차 실패 실험도 커밋하도록 요청했다. 시제품5종·검사 도구·원시 결과·인계38개 파일을 `dbde5b5`로 main에 커밋·푸시했다. 선택 엔진은v4이며 실패 후보를 승격하지 않았다.

다음 요청은 원본 Supertonic 3의 서버 형식을 우리 엔진에서도 제공하고 Mac 로컬에서 스트리밍을 검증하는 것이었다. 이번에는1코어·1GB 서버를 사용하지 않았다. 과거 ARM PR은 B 모델 측정이며 최신 F1200/retime의 ARM RTF가0.2대로 유지되는지는 확인하지 않았다.

## 구현

설치된 Supertonic Python1.3.1의 server/schema/route와 현재 공식 문서를 확인했다. 원본의 `/v1/tts`, `/v1/audio/speech`, `/v1/tts/batch`, `/v1/health`, `/v1/styles`, `/v1/styles/import` 요청 형식을 맞추고 PCM·SSE 스트리밍을 추가했다. 원본 설치 버전의 서버에는 스트리밍 경로가 없었다. FastAPI·Uvicorn 문서는 Context7에서 확인했다. 설치 의존성은 requirements-serve.txt와 테스트용 requirements-serve-test.txt로 분리·고정했다.

- `serve.py`: 로컬 실행 명령. 모델 경로 선택, 기본127.0.0.1:7788, worker1.
- `server.py`: 모델1회 로드·음색 재사용, 호환 API, 한 전용 추론 worker, 제한된 대기, JSON 오류, PCM/SSE 전송, 연결 취소 처리.
- `streaming.py`: 문장·문단 경계를 고려한 분할, 긴 무구두점 입력 상한, 묶음 사이 선택 무음, 네이티브44.1kHz PCM 변환.
- `runtime.py`: 호출별 음색을 읽기 전용으로 넘기고 ONNX 연산 사이에 취소 여부를 확인하는 선택 인자만 추가. 기존 호출 형식과 기본 수학·가중치·배속 경로 유지.
- `web/streaming.html`: 생성 즉시 재생, 중지, 정상 완료된 WAV 저장, 첫 소리·RTF·묶음 수 표시.

스트리밍은 텍스트 묶음마다8회 denoising과 보코더를 완료한 뒤 보내는 방식이다. 전체 문서 생성 완료 후 파일만 조각내는 방식이나 단일 문장 내부 causal decoding으로 설명하지 않는다. 실제 PCM을 약40ms body로 나누지만 이것이 모델의 첫 생성 지연40ms를 뜻하지 않는다.

모델은 기존 F1200·retime-g135 그대로이며 추가 학습·새 가중치·HF 업로드가 없다. Mac은 표준 ORT CPU 경로이고 EPYC용 AVX2 v4는 변경하지 않았다. 보정은 현재2.0×에서만 적용된다.

## 검증과 측정

`tests_server.py`13개 검사는 호환 경로, PCM/WAV/SSE 동일성, 배치 기본값, 음색 가져오기와 잘못된 shape, 형식·스텝·배속 검증, queue full·상태 응답, 스트리밍 시작 후 실패, 헤더 전송 실패 시 자원 반환을 포함한다. 기존 원본 공식 실행기와의 `tests_runtime.py`2개 float32 일치 검사도 통과했다.

실제 ONNX+임시 로컬 Uvicorn TCP 검사(`results/round11_streaming_runtime.json`):

- M1/F1 ×1.0/2.0, 각3묶음의 전체 WAV와 PCM 스트리밍을 대조했다. 두 경로 모두 vector 호출은24회, 즉 묶음당8회였다.4쌍 PCM16이 같았다.
- ONNX 호출은 전부 `tts_0` 하나에서 실행됐고 ORT intra/inter thread도1이었다.
- 처음부터 취소한 요청은 vector 호출0회였다.
- 전체216회 예정인 긴 요청의 첫 오디오를 받은 뒤 실제 TCP 연결을 닫았다.8회 뒤 중단됐고 admission이 반환됐다. 후속 생성은200이며 약0.091초 만에 회복했다. 이 수치는 시험 당시 값이며 보편적 취소 지연 보장이 아니다.

실제 서비스 포트의 측정은 TestClient 버퍼링을 쓰지 않고 httpx TCP stream에서 첫 `audio` 이벤트를 읽을 때까지 측정했다. KO/EN·M1/F1·1.0/2.0의8조합, 각각 warm-up 뒤2회다. 기본 목표 길이는 첫 묶음 KO60/EN120자, 나머지 KO120/EN240자이며 완성 문장은 상한 안에서 보존한다.

`results/round11_mac_streaming.json`에 전체값을 남겼고16회 PCM16은 같은 분할의 전체 응답과 전부 같았다. 생성 시간은 추론 합산이며 음성 길이는 설정한 묶음 간 무음도 포함한다. 인코딩·네트워크·수신을 포함한 wall RTF도 별도 기록했다. SSE 도착 시각과 초기100ms 여유를 이용한 버퍼 시뮬레이션에서는 끊김0이었지만 실제 오디오 장치 검사나 ARM 보장은 아니다.

첫 목표10자를 지정한 별도8조합×2회도 실행했다(`round11_mac_first_sentence.json`). 조합별 첫 PCM 중앙값은 약0.050~0.237초였고 대부분0.05~0.07초였다. F1 KO2×의 느린 값도 보존했다. 이때도16회 PCM이 같은 분할의 전체 응답과 같았다. 분할이 달라져 파형도 달라질 수 있으므로 이를 같은 음성의 엔진 가속률로 제시하지 않는다. 첫 묶음이 너무 짧으면 더 느린 장치에서 다음 묶음을 기다릴 수 있어 기본값은 바꾸지 않았다.

## 사용자 청취와 정정

사용자는 스트리밍 재생 연결에는 문제가 없다고 답했다. 처음1.5배속의 일부 생략이라고 표현했지만 이후 **일부 발음이 뭉개진다는 뜻이었다고 정정**했다. 이 피드백에서 단어 누락이 확인됐다고 기록하지 않는다. 현재1.5배속 발음 뭉개짐은 미해결이며2.0 전용 retime 보정을 중간 배속으로 자동 확대하지 않았다.

요청에 따라 배속 드롭다운을 숫자 입력으로 교체했다. UI와 모든 생성 API에서0.70~2.00·소수점 두 자리까지 허용한다. 브라우저1.25 입력과 스트리밍 생성을 확인했다. 실제 포트에서도1.25/1.30은200,1.251은422였으며 단위 검사에 native·호환·batch 경로의 정밀도 제한을 포함했다. 중간 배속 입력 가능 여부는 발음 품질 해결과 구분한다.

## 재개 지점

실행·프로토콜·취소·제한·재검사 방법은 [서버 안내](../../docs/SERVER.md)에 있다. 최신 집계는 [round11_state.json](round11_state.json), 상세 원시는 results/round11_*.json이다. API와 스트리밍이 실제로 실행된 것을 검증했고 새 WER/CER/MOS는 측정하지 않았다. 샘플 WAV·서버 로그는 Git 제외 경로에 보관한다.

다음 품질 과제는 사용자가 보고한1.5× 발음 뭉개짐의 구간·음색을 재현하고, 원본 최대 품질 교사·실제8회·기존 가중치 보존 원칙 안에서 원인을 구분하는 것이다. 원래2×에서 관측했던 누락과 이번1.5× 청취 피드백을 섞지 않는다. ARM 재측정은 사용자가 나중에 제공할 결과를 기다리며 별도 접속을 요구하지 않는다.
