# 13차: 정확한 행 병렬 정규화와 RTF 개선

## 출발점과 최종 선택

사용자는 앞선 개선을 커밋하고 RTF를 계속 낮추도록 요청했다. 12차는 이미 main `dfd138f`로 커밋·푸시돼 있었으며, 변경 없는 상태에서 후속 실험을 시작했다. 별도 브랜치를 만들지 않았다.

최종 선택은 **12차 조건 캐시 + ARM64 행 병렬 FP32 정규화**다. F1200 가중치·양자화 값·실제 denoising 8회·추론 한 스레드·기존 배속 설정을 유지한다. 새 학습·교사 생성·모델 축소·후처리가 없다. 표준 ORT와 Linux x86 AVX2 v4는 기존 경로로 사용할 수 있다. 이번 성능 실측은 M4 Max이며 Oracle ARM·EPYC 서버는 사용하지 않았다.

## 시도한 후보와 채택 판단

각 행은 직전 12차 패키지와 순서를 바꾼 warm 교대 비교다. 값은 조합별 쌍별 시간 감소율 중앙값들의 중앙값이며 양수일수록 빠르다. 1/2배속 후보는 8조합, 중간 배속까지 포함한 후보는 12조합이며 각각 6쌍이다.

| 시도 | 생성 시간 감소율 | 판단 |
| --- | ---: | --- |
| GELU 전후 역전치 56개 제거 | 0.09% | 미채택. 최적화된 그래프의 연산 수가 같고 이득이 거의 없음 |
| BiasGelu 28개를 직접 사용 | -1.47% | 미채택. 파형은 같지만 대부분 느려짐 |
| 실제 API의 배치 크기 1 명시 후 조건 재분리 | 0.87% | 미채택. 추가 49개 연산을 캐시했지만 이득이 작고 일부 조합은 느려짐 |
| 배치 고정 + 스텝 전용 조건을 엔진 로드 때 계산 | 0.81% | 미채택. 52개 연산·4개 경계 텐서를 분리했지만 일관된 이득이 부족 |
| **행 병렬 정규화 36곳** | **8.24%** | **채택. 12조합 모두 개선, 후속 HTTP·파형 검사 통과** |

앞의 4개는 학습 후보가 아닌 엔진 실험이다. `experiments/transpose_free_gelu.py`의 `--bias-gelu`까지 포함해 재현 코드를 보관했다. 저장된 코드가 실제 측정했던 BiasGelu 그래프를 같은 SHA-256으로 만드는 것도 확인했다. 배치 고정 실험의 첫 보존 검사는 split이 사용하지 않는 scalar Gather index를 제거해 실패했다. 그 상수도 보존하도록 수정한 뒤 측정했다. 학습 가중치 변경은 없었다.

스텝 캐시는 문장·음색과 무관한 시간 조건만 현재 기기의 ORT로 시작할 때 계산하는 선택 기능이다. 그 실험 그래프의 로드 지원과 재현 도구는 보관하지만 선택 패키지에는 적용하지 않는다. Mac에서 계산한 상수를 ARM 서버에 고정해 넣지 않는다.

## 정규화 커널

12차 프로파일에서 정규화가 vector 노드 실행 시간의 약 28%를 차지해 조사했다. 공개된 [ORT CPU 정규화 구현](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cpu/nn/layer_norm_impl.cc)을 참고하고, 실제 설치된 ORT 1.31.1과 작은 연산을 직접 비교했다.

한 행의 512개 채널을 처리하는 순서를 바꾸지 않고 **독립된 4개 행을 NEON 4개 lane에서 함께 진행**한다. 행 내부 Welford 평균·분산 갱신 순서는 유지한다. 나눗셈을 역수 근사로 바꾸지 않으며 제곱근도 그대로 계산한다. 실험 초기에는 FMA를 모두 끈 경우와 M2 갱신에만 FMA를 쓴 경우에 작은 오차가 있었다. 측정한 ORT와 같은 두 위치인 M2 갱신·최종 affine에 명시적 FMA를 사용했을 때 일치했다. 따라서 이것을 모든 컴파일러·ORT의 보편적인 동작으로 가정하지 않는다.

- `native/row_norm.c`: 로컬 변수만 사용하는 단일 스레드 커널과 ORT C API adapter. 읽기 전용 가중치, 개별 호출의 입력·출력을 사용한다.
- `native/build_row_norm.py`: 현재 ARM64 기기에서 빌드한다. `-ffp-contract=off`와 두 명시적 FMA 위치를 사용한다. 임시 바이너리를 만든 뒤 교체해 실행 중인 파일을 직접 덮어쓰지 않는다.
- `row_norm_ops.py`: 설치된 CPU ORT와 1/4/5/81개 행의 결과를 바이트 비교한다. 다르면 실행을 거부한다.
- `prepare_row_norm.py`: 벡터 추정기의 FP32·마지막 축·폭 512인 정규화 36곳만 교체한다. 원본 initializer는 직렬화 바이트까지 보존한다. 완성된 패키지만 공개하고 복사·하드 링크 모두 지원한다.
- `runtime.py`: 패키지가 선택한 경우만 커널을 등록한다. CPU 스레드·연산 단계·배속의 수학을 바꾸지 않는다.

Linux ARM64용 빌드 경로도 제공하지만 이 기기에서는 빌드·실행하지 않았다. 설치된 ORT가 다른 수치 규칙을 쓰면 시작 시 거부할 수 있으며 그 경우 표준 패키지를 사용한다. 기본 표준 모델에는 네이티브 라이브러리가 필요 없다. C API 헤더의 MIT 고지와 자체 커널 코드를 구분해 보관한다.

## 성능 측정

M4 Max·CPUExecutionProvider·ORT intra/inter thread 1/1이다. 각 쌍의 실행 순서를 번갈아 바꾸고 워밍업 뒤 측정했다. 모델 로딩·빌드·호환 검사·프로파일링·파일 저장은 생성 시간에 포함하지 않는다. 두 모델을 같은 프로세스에 로드한 RSS는 단일 엔진 메모리로 주장하지 않는다.

짧은 KO/EN × M1/F1 × 1.0/1.5/2.0×의 12조합, 각각 6쌍에서 **생성 시간 감소율 중앙값 8.24%**, 조합별 약 4.91~11.25%였다. 모든 비교에서 기준과 같은 수치의 파형을 확인했다. 후속 바이트 검사는 이 설정들도 포함한다. [원시 생성 비교](../../results/round13_row_norm_paired.json)

실제 임시 Uvicorn 서버와 TCP로 8조합 × 6쌍의 스트리밍 요청을 한 번에 하나씩 실행했다. PCM은 모두 기준 출력과 일치했다.

| 조합 | 12차 생성 RTF 중앙값 | 정규화 후보 생성 RTF 중앙값 | 쌍별 HTTP 전체 시간 감소율 중앙값 |
| --- | ---: | ---: | ---: |
| M1 KO 1.0× | 0.03345 | 0.03031 | 9.14% |
| M1 KO 2.0× | 0.04565 | 0.04160 | 8.64% |
| M1 EN 1.0× | 0.03338 | 0.03039 | 8.86% |
| M1 EN 2.0× | 0.04591 | 0.04178 | 9.07% |
| F1 KO 1.0× | 0.03273 | 0.02960 | 9.00% |
| F1 KO 2.0× | 0.04647 | 0.04221 | 9.16% |
| F1 EN 1.0× | 0.03375 | 0.03098 | 7.53% |
| F1 EN 2.0× | 0.04680 | 0.04083 | 10.29% |

HTTP 8조합의 감소율 중앙값은 **생성 합계 9.35%, 전체 응답 시간 9.04%, 첫 오디오 9.03%**였다. 모든 조합이 개선됐고 전체 시간 감소율은 약 7.53~10.29%였다. RTF는 추론 합계와 설정된 묶음 사이 무음을 포함한 음성 길이로 계산한다. 전체 HTTP 시간에는 인코딩·전송·수신 비용이 들어간다. 쌍별 감소율의 중앙값이므로 표의 별도 RTF 중앙값 비율과 다를 수 있다. [원시 HTTP 비교](../../results/round13_row_norm_http.json)

공개된 uncached retime 패키지와 최종 후보도 별도로 8조합 × 6쌍 비교했다. **조건 캐시 + 정규화의 생성 시간 감소율 중앙값은 11.07%**였다. 이전 4.01%와 이번 8.24%를 더한 수치가 아니다. [공개 패키지부터의 직접 비교](../../results/round13_public_to_selected.json)

## 출력·서버·배포 검사

`experiments/check_portable_cache.py`에 직접 바이트 비교와 case/speed 선택을 추가했다. M1/F1/M5/F5 × KO/EN 짧은 문장·장문 × 0.70/1.00/1.25/1.30/1.50/2.00×의 **96쌍 float32 바이트가 일치**했고, 각 생성이 vector를 실제 8회 호출함을 세었다. 수치 동등성과 signed zero까지 구분하는 바이트 동등성을 함께 확인한다. [엄격한 파형 검사](../../results/round13_strict_waveforms.json)

`tests_row_norm.py` 6개 검사는 설치된 ORT와 native 결과 비교, 잘못된 affine shape·축 거부, 호환 검사 실패 거부, 복사·하드 링크 시 원본 보존, 실패 시 정리를 포함한다. 수치 비교는 10개 행 길이 × 2개 epsilon × 5개 입력 분포의 100개 하위 사례다. 랜덤·작은 값·큰 값·상수·큰 offset을 사용했고 바이트까지 같았다. `tests_server.py` 13개, 공식 원본 실행기와 비교하는 `tests_runtime.py` 2개도 통과했다.

실제 네이티브 서버에서 M1/F1 × 1.0/2.0×의 각 3묶음은 전체 응답·스트리밍 모두 vector 24회였고 4쌍 PCM이 같았다. 호출 스레드는 `tts_0` 하나, ORT 설정은 1/1이었다. 216회 예정 요청을 첫 오디오 후 취소했을 때 8회에서 멈췄고 다음 요청은 정상 처리됐다. 회복 약 0.086초는 시험 당시 관측값이다. [실제 호출·취소 결과](../../results/round13_row_norm_runtime.json)

`package_runtime.py`는 이 경로를 선택하면 컴파일된 바이너리 대신 C 소스·빌드 도구·API 헤더를 포함한다. `experiments/check_runtime_package.py`로 새 폴더에 추출해 빌드하고 실제 1.25× 음성을 생성했다. 기준 파형 SHA-256이 같았으며 임시 압축 파일과 추출 폴더는 제거했다. 첫 검사 harness에서는 가상환경 Python의 symlink를 resolve해 시스템 Python을 선택하는 문제가 있었고, symlink를 유지하도록 수정했다. [패키지 검사](../../results/round13_package_check.json)

최종 준비 도구가 실제 측정한 그래프와 같은 바이트를 만드는 것도 확인했다. 7788 청취 서버는 선택 패키지로 재시작했으며 상태 200·8스텝·한 스레드·음색 10개를 확인했다. 실제 생성에서 1.25/1.30은 200, 1.251은 422였다. [청취 서버 검사](../../results/round13_demo_smoke.json)

## 보관·재현·다음 작업

실패 후보 4개 패키지와 진단용 네이티브 라이브러리를 지웠다. 기준 모델·12차 패키지·최종 13차 패키지는 유지했다. 삭제 후보들이 독점하던 inode의 파일 크기 합은 약 190MB이며 실제 APFS 물리 회수량을 측정한 값은 아니다. 초기 패키지 검사 압축 파일도 지웠다. [정리 목록과 그래프 해시](../../results/round13_cleanup.json)

새 가중치가 없으므로 HF에 모델을 중복 업로드하지 않았다. Git에는 소스·작은 JSON·문서만 추가하며 컴파일된 라이브러리·모델·음성·로그·개인 경로는 제외한다. 실행은 [서버 안내](../../docs/SERVER.md#arm64-행-병렬-정규화-선택), 재현 명령과 상태는 [round13_state.json](round13_state.json)에 있다. main에 성공한 최적화를 커밋·푸시한다.

새 WER/CER/MOS는 측정하지 않았다. 기준 파형의 바이트 보존은 기존 품질 한계도 보존한다. 사용자가 정정한 **1.5배속 일부 발음 뭉개짐은 미해결**이며, 단어 누락으로 확인됐다고 기록하지 않는다.

다음 조사 대상은 독립 행 타일을 더 크게 잡아 같은 연산의 대기 시간을 줄이는 방법, 남은 동적 INT8 행렬곱·정확한 GELU의 비용이다. 더 큰 행 타일도 같은 행 내부 연산 순서·바이트 일치·실제 HTTP 성능·메모리를 확인한 뒤 채택해야 한다. FastGELU·새 양자화·모델 축소를 이번 결과에 섞지 않는다. ARM 서버 측정은 사용자가 추후 제공할 결과로 별도 검증한다.
