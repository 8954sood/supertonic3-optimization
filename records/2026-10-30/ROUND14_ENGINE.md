# 14차: 16행 정규화와 계층적 잔여 처리

13차 main `4b47bbd`에서 시작했다. F1200·양자화·실제 8회·추론 한 스레드를 유지하고, 그래프와 가중치를 바꾸지 않았다. 이번 선택은 16행 NEON 정규화와 8→4→개별 행의 잔여 처리다. 모델 폴더는 기존 `models/round13-row-norm`을 그대로 사용한다.

## 후보와 고정 기준

기존 13차의 컴파일된 4행 라이브러리를 별도 파일로 동결했다. 기준 소스는 Git `4b47bbd:native/row_norm.c`이며 SHA와 바이너리 SHA는 `results/round14_reference_build.json`에 있다. 바이너리는 Git에 넣지 않는다. 재현할 때 이 Git 버전의 C 소스를 별도 폴더에 복원하고 기존 `-O3 -ffp-contract=off -DFUSED_M2 -DFUSED_OUTPUT`로 빌드한다.

8·16·32행을 비교했다. 한 행의 채널 처리 순서, 두 FMA 위치, 나눗셈과 제곱근은 그대로다. 큰 묶음에서 남는 행을 전부 4행으로 보내던 flat 방식도 시험했다. 이후 32→16→8→4 및 16→8→4 방식으로 잔여 구간을 처리했다. 계산 결과는 같고 독립 행들의 명령만 교차 배치한다. 추가 스레드나 모델 파라미터가 없다.

초기 flat 후보의 소스도 `round14_restore_flat.patch`로 복원할 수 있으며 당시 빌드 영수증의 소스 SHA와 같음을 확인했다. 해당 패치는 이 차수의 계층적 C 소스 복사본에 `git apply --unidiff-zero`로 적용하는 복원용이다. 초기 C 직접 호출 스크리닝과 후속 순서 균형 스크리닝은 전체 TTS RTF가 아니다. `experiments/benchmark_row_tiles.py`는 모든 순서 위치를 순환한 뒤 역순으로 측정한다.

## 성능

M4 Max·CPUExecutionProvider·intra/inter 1/1이다. 모델 로드·네이티브 빌드·호환 검사·프로파일링을 제외한 warm 생성 시간을 측정했다. 두 엔진은 같은 그래프를 로드하고 다른 검증된 커널 라이브러리를 사용한다. 각 쌍의 순서를 번갈아 바꾸며 동시 추론하지 않는다.

- 초기 flat16 대 row4: 12조합 모두 개선됐다. 원시는 `round14_r16_paired.json`이다.
- 계층적32 대 row4: 조합별 쌍별 생성 시간 감소율 중앙값 4.16%였다.
- 계층적32 대 계층적16: 같은 집계로 -0.061%였다. 조합별 방향이 섞여 32행의 일관된 우위를 확인하지 못했다. 최대 묶음이 작은 16행을 선택했다.
- 최종 계층적16 대 고정 row4: 12조합 × 6쌍의 생성 시간 감소율 중앙값 **3.30%**였다.
- 실제 TCP 스트리밍 8조합 × 6쌍: 전체 응답 시간 감소율 중앙값 **3.82%**, 추론 합계 **3.94%**, 첫 오디오 **3.12%**였다. 8조합 모두 쌍별 HTTP 시간 감소율이 양수였다.

| --- | ---: | ---: | ---: |
| M1 KO 1.0× | 0.02823 | 0.02823 | 3.33% |
| M1 KO 2.0× | 0.03981 | 0.03878 | 2.44% |
| M1 EN 1.0× | 0.03055 | 0.02932 | 4.22% |

M1 KO 1.0×는 별도 RTF 중앙값끼리 비교하면 거의 차이가 없다. 쌍별 시간 비율을 집계한 중앙값과 각 실행 집단의 시간 중앙값 비율은 서로 다른 통계량이므로 구분한다. RTF의 음성 길이는 설정한 묶음 간 무음을 포함한다. HTTP 시간에는 인코딩·전송·수신 비용이 포함된다.

공개 uncached retime 패키지와 최종 기본 빌드도 별도로 8조합 × 6쌍 비교했다. 생성 시간 감소율 중앙값은 **15.28%**였다. 기존 개선율을 더하거나 서로 다른 배치의 RTF를 나눈 수치가 아니다. 모든 수치는 Mac 관측값이며 Oracle ARM·1코어 EPYC의 성능으로 환산하지 않는다.

## 보존·실행 검사

같은 그래프와 가중치를 사용한다. M1/F1/M5/F5 × KO/EN 짧은 문장·장문 × 0.70/1.00/1.25/1.30/1.50/2.00×의 96쌍에서 float32 바이트가 기준 4행 버전과 같았다. 각 생성의 실제 vector 호출도 8회였다.

선택 빌드로 `tests_row_norm.py` 6개 검사를 통과했다. 23개 행 길이 × 2개 epsilon × 5개 분포의 230개 수치 사례를 바이트 비교했다. 8·16·32행 경계와 짧은 tail을 추가했다. 런타임 호환 검사도 1/4/5/8/9/16/17/32/33/81행으로 확대했다.

실제 스트리밍 호출·PCM·단일 worker·취소 후 정상 요청 검사는 `round14_streaming_runtime.json`에 있다. 선택 커널의 소스-only 실행 패키지를 추출해 빌드하고 실제 음성을 생성하는 검사도 통과했다(`round14_package_check.json`). 동일한 모델 폴더를 재사용하며 HF에 새 가중치를 업로드할 필요가 없다.

`native/build_row_norm.py`의 기본 행 수는 16이고, 다른 후보는 `--rows 4/8/16/32 --output <별도 라이브러리>`로 빌드한다. 새 소스를 받아도 기존 바이너리는 바뀌지 않으므로 재빌드와 서버 재시작이 필요하다. 두 라이브러리 비교는 `--reference-library`·`--candidate-library`를 사용하며, 각 라이브러리는 설치된 ORT와 일치 검사를 통과해야 한다. 커널은 실행 기기에서 빌드하고 Linux ARM64는 아직 실측하지 않았다.

## 다음 작업과 기록

새 프로파일 진단에서 벡터 추정기의 상위 연산은 DynamicQuantizeMatMul 약 37.0%, GELU 약 20.1%였다. 텍스트 처리기에는 폭 256의 정규화 15곳, 보코더에는 폭 512의 정규화 10곳, duration 처리기에는 폭 64의 정규화 10곳이 남는다. 현재 네이티브 변환은 벡터 추정기 36곳에만 적용돼 있으므로 이 구간을 다음 후보로 조사한다. 프로파일은 warm 호출을 포함하는 진단이며 비프로파일 가속률로 쓰지 않는다.

재현 명령·빌드와 기준 SHA는 `round14_state.json`, 원시 수치는 `results/round14_*.json`에 있다. 추가 ASR·WER·MOS를 측정하지 않았으며 파형 일치가 기존 F1200 품질 한계도 보존한다. 1.5배속 발음 뭉개짐은 여전히 별도 과제다. main에 이번 성공을 먼저 커밋·푸시한 뒤 남은 정규화 후보를 이어서 조사한다.
