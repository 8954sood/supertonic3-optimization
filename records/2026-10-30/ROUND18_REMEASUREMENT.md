# 18차: 엔진 버전별 동일 조건 RTF 재측정

## 목적과 사전 고정 조건

사용자가 과거 v2의 RTF 0.948/0.957이 최신 버전보다 낮은 이유를 물었고, 각 엔진 버전의 정확한 비교 수치를 요청했다. 과거 측정은 1.05배속, 이후 일부 표는 출력 2배속이므로 그대로 성능 순위를 매길 수 없다. 이번에는 같은 서버·런타임·학습 가중치에서 엔진만 교체한다. 실행 전 아래 조건과 반복 수를 고정했다.

- 대상: 기존 작업용 Linux x86_64 AMD EPYC 7551 서버, RAM 977100 KiB. Oracle ARM 서버의 결과가 아니다.
- CPU affinity `[0]`, nice 19, ORT intra/inter와 수치 라이브러리 각각 1스레드.
- F1200 가중치·양자화 고정, 실제 vector estimator 8회, seed 42, M1 음색.
- 같은 한국어·영어 짧은 문장. 장문·다른 음색의 일반 성능으로 확대 해석하지 않는다.
- 1.00배속과 출력 2.00배속을 별도 측정. 2배속은 기존 내부 1.35 → 출력 2.0 경로이다.
- v1/v2/v3 실험판/v4/v5 커널은 동일한 기존 native 그래프를 쓴다. `v5-package`만 이미 검증된 batch-one 그래프를 사용한다. Python 런타임은 모두 현재 버전으로 통일한다. 과거 각 버전의 전체 Python 스택을 복원한 실험은 아니다.
- 주요 6개 조건을 각 속도에서 6블록 반복. 각 버전이 각 실행 위치에 한 번씩 오도록 Williams 순서를 사용하고, 앞에 오는 버전의 조합도 균형을 맞춘다. 2배속의 버전 순서는 정배속의 역순이며 블록마다 속도 순서도 바꾼다.
- v2와 v5-package는 과거 기록 대조용 1.05배속도 6블록 AB/BA로 교대한다.
- 총 84개 새 프로세스, 각 프로세스에서 KO/EN 각각 예열 1회 + 측정 1회. 총 168개 측정 음성, 168개 예열 음성. 다른 모델의 동시 메모리 상주·동시 추론은 없다.
- RTF = 측정 wall time / 최종 음성 길이. 로딩·파일 쓰기·해시 계산은 제외한다. 서버 부하를 임의로 보정한 RTF는 쓰지 않는다.
- 모든 원시 측정값을 보존하며 느린 값도 삭제하지 않는다. 중앙값·최솟값·최댓값·사분위 범위와 같은 블록의 쌍별 시간 감소율을 구분한다.
- 모든 버전의 같은 속도·문장 출력은 float32 SHA-256·샘플 수·샘플레이트·텍스트가 같아야 한다. 실제 8회 호출과 세션 스레드 수를 매번 검사한다.
- 각 자식 프로세스 트리 RSS 480 MB / 시스템 여유 80 MB / 240초의 50 ms 표본 감시. OS 강제 메모리 상한은 아니다. 다른 사용자의 프로세스나 시스템 설정은 변경하지 않는다.

v1/v2/v4와 v5 라이브러리는 이전 검사에 쓴 버전별 바이너리를 그대로 사용한다. v3는 보존된 `experiments/exact_int8_v3.c`를 기존 znver1 빌드 설정으로 다시 빌드했다. 새 v3 바이너리는 서버에서 표준 ORT 정수 곱과 17개 경계·tail·cache 검사를 통과한 뒤 측정에 넣었다. v3는 당시 채택하지 않았던 실험판이라는 지위를 바꾸지 않는다.

## 예비 측정 중 발견한 빌드 차이

서버에 보존된 v2 빌드는 두 종류였다. 첫 예비 실행에서 사용한 `4237f3af…`는 7차 비교의 v2였고, 6차 공개 빌드 영수증과 9차 비교의 기준은 `7beea5a7…`였다. `.rodata`와 `.data`는 같지만 `.text`와 `.eh_frame`이 달랐다. 같은 v2 알고리즘이라는 이유로 빌드 차이를 무시하지 않았다. 불완전한 예비 실행 전체를 제외하고 **공개 빌드 SHA-256 `7beea5a751d8572338417934201b9e21d775fa124601e5bd2c11926c494c3dc1`**를 고정해 84개 프로세스의 프로토콜을 처음부터 다시 시작했다. 첫 예비 수치는 최종 표에 섞지 않는다.

예비 원본은 로컬 비공개 작업 폴더와 서버 작업 폴더에 보존하며, 제외 이유·완료 프로세스 수·원본 SHA-256·소스 commit과 SHA-256은 `results/round18_provenance.json`에 남긴다. 최종 실행 중에는 시간에 따른 제외 기준을 새로 만들지 않는다. 기존 active 라이브러리와 기본 선택 모델은 변경하지 않았다.

## 재현

드라이버는 `experiments/remeasure_engine_versions.py`이다. 설정 파일은 이름·모델 경로·라이브러리 경로를 가진 `variants`와 다음 두 `groups`를 갖는다.

```json
{
  "groups": [
    {"name": "main", "variants": ["v1", "v2", "v3-experimental", "v4", "v5-kernel", "v5-package"], "speeds": [1.0, 2.0]},
    {"name": "historical", "variants": ["v2", "v5-package"], "speeds": [1.05]}
  ]
}
```

```bash
python experiments/remeasure_engine_versions.py \
  --config round18_config.json --output results/round18_engine_versions.json --blocks 6
```

84개 새 프로세스가 모두 완료됐다. 원본은 `results/round18_engine_versions.json`, 집계는 `results/round18_summary.json`, 실제 경로 설정은 `results/round18_config.json`이다. 과거 수치와 새로운 수치를 혼합해 개선율을 계산하지 않는다.

## 해석과 제한

> **측정 환경 주의:** 이 서버는 1코어·약 1GB RAM의 매우 낮은 사양이며, 다른 프로세스도 함께 실행 중입니다. 가용 CPU·메모리와 공유 부하의 영향으로 반복 측정값과 버전 간 성능 비교의 일관성이 낮습니다. 아래 RTF는 해당 환경에서 관측한 값이며, 안정적인 성능 보장이나 작은 차이의 확정적인 순위로 해석하지 마세요. 여유 있는 전용 환경에서 별도 재검증이 필요합니다.

v4 대비 현재 v5 패키지의 영어 정배속은 쌍별 시간 감소율 중앙값 −15.94%, v5 엔진만 적용한 경로 대비 −14.42%였다. 후자의 6쌍 모두 패키지가 느렸다. 따라서 이번 결과로 최신 패키지의 보편적인 가속을 주장하지 않는다. 반면 v2 대비 패키지의 영어 정배속은 RTF 중앙값이 높아도 쌍별 감소율 중앙값 +2.67%, 4/6쌍 빨라짐이다. 서로 다른 통계를 같은 개선율로 취급하지 않는다.

일부 지연에서는 바꾸지 않은 단계도 늘었다. 예를 들어 블록 1의 v5 패키지 KO 2× RTF 2.8975에서 text encoder 약 0.283초·VE 5.597초·vocoder 2.199초였다. 블록 2의 EN 1× RTF 1.7547에서는 vocoder가 4.413초였다. 이 관찰은 공유 환경 영향 가능성을 보여 주지만 패키지·메모리 배치의 간접 영향을 배제하거나 원인을 확정하지 못한다. 느린 값을 이상치로 제거하지 않았다.

모든 guard가 통과했으며 표본 최대 프로세스 트리 RSS 391.569408 MB, 시스템 최소 available 115.421184 MB였다. 이는 단일 엔진·짧은 문장 범위이다. 같은 속도·문장의 168개 측정 파형이 바이트 일치했고, 매 예열·측정의 VE 호출이 실제 8회였다. 학습 가중치와 양자화는 바꾸지 않았으며 새로운 WER/CER/MOS를 측정하지 않았다. F1·장문·ARM의 일반 성능이나 지속 실시간 보장으로 확대 해석하지 않는다. 현재 모델·기본 라이브러리 선택은 바꾸지 않았다.

## 추가 진단 — v5 엔진 고정, batch-one 그래프만 교체

주 측정에서 현재 패키지의 EN 1× 지연이 반복돼, 측정을 모두 끝낸 뒤 이 조건만 추가했다. 같은 v5 라이브러리 `32008e09…`를 양쪽에 사용하고 native 기본 그래프 / batch-one 그래프를 비교했다. SHA와 설정이 같은 frontend·condition·vocoder를 공유하고 VE 세션만 두 개 상주시켰다. M1·EN short·1.0×·실제 8회·CPU0·1스레드·nice19·10쌍이며 AB/BA 5쌍씩을 seed1801로 섞었다. 동시 추론은 하지 않았다.

일반 그래프 RTF 중앙값 **1.008784**, batch-one **1.007043**, 쌍별 시간 감소율 중앙값 **-0.187547%**, 빨랐던 쌍 **4/10**이다. 모든 파형·실제 8회 검사가 통과했다. 큰 지연이 그대로 재현되지 않아 fresh-process 결과를 곧바로 그래프 자체의 고정 회귀율로 해석하지 않는다. 주 측정의 느린 실행은 삭제하거나 이 진단으로 대체하지 않는다.

이 진단의 표본 최대 프로세스 트리 RSS는 459.587584 MB, 시스템 최소 available은 209.473536 MB였다. VE 두 세션의 추가 메모리는 벤치마크 비용이므로 운영 단일 엔진 메모리와 혼합하지 않는다. 원본은 `results/round18_batch_diagnostic.json`, guard는 `results/round18_batch_diagnostic_guard.json`이다. 서버 기본 runtime·active 라이브러리가 바뀌지 않았음은 `results/round18_server_integrity.json`, 모든 주 측정 원본 복원·RTF·중앙값 재계산 검사는 `results/round18_data_checks.json`에서 확인한다.

## 남은 판단

이번 저사양·공유 환경에서는 작은 차이의 성능 순위를 안정적으로 확정하지 못했다. 엔진 선택·학습 가중치·기본 모델은 변경하지 않고, 여유 있는 전용 환경에서 F1·장문을 포함한 재검증을 권장한다. 후속 최적화는 fresh-process와 공유 frontend 진단의 차이, 메모리 배치·공유 부하·vocoder 지연을 분리하는 일부터 시작한다. ARM 결과로 환산하지 않는다.
