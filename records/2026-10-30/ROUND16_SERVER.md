# 16차: 실제 1코어·1GB EPYC 재측정

main `7db1daa` 이후 사용자가 기존 1코어·1GB 서버의 실제 측정을 요청했다. 다음 지시에서 v5 엔진 개발을 추가했다. 이 차수는 v5를 고르기 전의 기준선이다.

## 환경과 적용 범위

AMD EPYC 7551 x86_64, 물리 코어 ID 0의 SMT 형제 0/1이 허용돼 있으나 추론은 논리 CPU 0 하나로 고정했다. 총 RAM은 약 1000.55MB(977100KiB), Python 3.12.3·ORT 1.31.1·NumPy 2.5.4·Supertonic 1.3.1이다. nice19, ORT intra/inter 1/1, 환경변수의 수치 라이브러리 스레드도 1이다. 기존 프로그램과 스왑을 공유하며 새로운 CPU quota나 cgroup을 만들지 않았다.

14/15차 ARM64 NEON 정규화는 이 CPU에서 실행할 수 없다. 실제 로더도 ARM64가 필요하다는 오류로 거부했다. 따라서 최신 Mac의 19.32% 개선율을 이 서버에 적용한 결과로 해석하지 않는다. x86 전용 v4 라이브러리와 이식 가능한 표준 조건 캐시를 측정했다. 학습 가중치·양자화·8회·기존 내부 1.35/출력 2.0 경로는 고정했다.

기존 서버 작업 공간의 runtime/모델/라이브러리를 덮어쓰지 않고 `round16-eval`에 격리했다. 공유하는 frontend 세 그래프의 SHA를 검증한 뒤 읽기 전용 하드 링크로 재사용했다. 새 표준 패키지의 vector/condition/manifest만 별도로 옮겼다. v4 라이브러리 SHA는 `0f0d97f2659831a2bab785a2f20f96977a732170cf5119988499266c7e3a83cf`다. 전체 환경·코드 SHA는 `round16_epyc_snapshot.json`에 있다.

처음 모든 모델을 확인하는 작업에서 큰 가중치를 한 번에 읽어 메모리 부담이 생겨, 이 작업으로 시작한 확인 프로세스만 중단했다. 이후 해시는 1MiB 단위로 읽는다. 이 확인 작업의 시간은 추론 성능 수치로 사용하지 않았다.

## 비교 방법과 결과

기존 서버 runtime+v4, 최신 runtime+v4, 최신 runtime+표준 조건 캐시의 세 설정을 회전·역순으로 실행했다. 속도 1.0/2.0 × KO/EN 짧은 문장을 세 쌍씩 비교했다. 모델 하나를 담은 새 프로세스만 실행하며, 각 문장을 한 번 워밍업한 다음 한 번의 생성 시간을 측정했다. 모델 로드·해시·결과 파일 저장은 생성 RTF에서 제외했다.

| 조합 | 기존 runtime + v4 | 최신 runtime + v4 | 최신 표준 조건 캐시 |
| --- | ---: | ---: | ---: |
| ko_short 1.0× | 1.0101 | 1.0368 | 1.1482 |
| en_short 1.0× | 1.0094 | 1.0352 | 1.1596 |
| ko_short 2.0× | 1.4001 | 1.3663 | 1.5375 |
| en_short 2.0× | 1.3487 | 1.3500 | 1.5956 |

개별 쌍에서 실행 시간 변동이 컸다. 최신 v4의 정배속 영어는 1.0352/1.6273/1.0026의 RTF를 기록했다. 가장 빠른 실행을 선택하지 않고 세 실행의 중앙값과 원시값을 보존했다. 이 결과만으로 최신 Python runtime이 x86에서 일관되게 빨라졌다고 주장하지 않는다. 표준 경로도 v4를 대체할 속도 이득이 없었다.

추가 최신 v4 검사에서 짧은 1.5×는 KO 1.0514 / EN 1.0432(워밍업 후 3회 중앙값), 장문 1.0×는 KO 1.0074 / EN 1.0148, 장문 2.0×는 KO 1.3944 / EN 1.3727이었다(장문은 각 1회). 보조 검사의 단독 RTF를 앞의 쌍별 개선율로 사용하지 않는다.

## 메모리와 출력

모든 21개 프로세스가 guard를 통과했다. 50ms 표본으로 자기 자식의 프로세스 트리 RSS 480MB, 시스템 available 80MB, 작업별 시간 상한을 감시했다. 전체 표본 최대 RSS는 **427.33MB**, 최소 system available은 **203.17MB**였다. 이는 샘플 감시이며 OS의 강제 제한이 아니다.

각 완료된 생성의 vector 호출은 실제 8회였다. 주 비교의 두 속도·두 문장·세 쌍에서 기존 v4와 최신 v4 및 표준 경로의 float32 SHA와 샘플 수가 모두 같았다. 추가 ASR/WER/CER/MOS를 측정하지 않았다. 기존 발음 한계도 그대로다.

원시는 `results/round16_epyc_benchmark.json`, 집계는 `round16_epyc_summary.json`, 환경은 `round16_epyc_snapshot.json`이다. `experiments/benchmark_server_case.py`는 실제 호출 수·CPU 시간·파형 해시를 기록하고, `experiments/summarize_server_round16.py`는 집계를 재현한다. 후속 `paired_server_engines.py`는 별도 라이브러리 인자를 써 active 라이브러리를 교체하지 않는 비교 도구다.

이 서버는 정배속에서 실시간 경계, 2배속에서는 실시간보다 느린 상태다. 사용자의 후속 지시에 따라 이 기준선을 보존하고 x86 v5를 조사한다. ARM 서버 실측이나 새 모델 학습은 이번 차수에 없다.
